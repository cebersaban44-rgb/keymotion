An AJAZZ AK980 PRO runs one of two firmware generations, and they speak different command families. This site names each family after the first byte of its commands:

| | "04 xx" family | "AA" family |
|---|---|---|
| Firmware | 1.06 (USB `bcdDevice` `0x0106`) | 769, shown as 3.01 (`0x0301`) |
| USB IDs on the cable | `0C45:8009` | `0C45:8039` |
| Commands | 64-byte feature reports on `FF13`, in sessions | 64-byte output reports on `FF68`, each answered with an input report |
| Screen | 4096-byte pages on `FF68` | 4104-byte packets on `FF67` |
| Code | `kb_protocol::sonix`, `kb_core::sonix` | `kb_protocol::aa`, `kb_core::aa` |
| Measured on a real keyboard | yes | not yet ([what is open](#still-unverified-on-a-real-769)) |

The sections up to [What is blocked, and why](#what-is-blocked-and-why) describe firmware 1.06, as measured on one keyboard in November 2026 with the `kb` developer tool and the app itself. The code that implements them is in `crates/kb-protocol` (packets), `crates/kb-core/src/sonix.rs` (sessions and timing) and `crates/kb-devices/models/ajazz-ak980-pro.toml` (the model). [The "AA" family](#the-aa-family-firmware-769) describes firmware 769. AJAZZ publishes neither protocol, and Keymotion is not affiliated with AJAZZ.

<Aside type="caution" title="A reference, not a recipe">
Several of these commands write the keyboard's permanent memory. Don't send them by hand: use the app or `kb`, which validate every value and pass every packet through the safety guard. Only firmware 1.06 has been tested on a real keyboard; other versions may behave differently. `kb` speaks the "04 xx" family only.
</Aside>

## Identity and connection modes

A switch on the back picks the connection. From left to right it reads **2.4G · USB · BT**; USB is the middle position. Settings travel only over the USB cable.

| Mode | How Windows sees it | What Keymotion does |
|---|---|---|
| USB cable | VID `0C45`, PID `8009`. Manufacturer string `SONiX`, product string `AK980 PRO`. | Everything. The app matches VID, PID, the USB bus and "AK980 PRO" in the product name. |
| Bluetooth | Name `AK980 PRO-1`; the suffix is the Bluetooth channel. PnP ID: VID `0C45`, PID `FEFE`, version `0x0138`. | Reads the battery level. There is no vendor channel over Bluetooth. |
| 2.4 GHz receiver | VID `0C45`, PID `FEFE` on the USB bus, with a vendor collection on usage page `FF60`. This comes from the model file and has not been measured here. | Shows that the receiver is plugged in. Nothing is sent to it, so whether the keyboard behind it is on is not known. |

The receiver and Bluetooth share `0C45:FEFE`, so the app tells them apart by bus. The receiver shows up whether or not the keyboard is on; when the keyboard is connected over Bluetooth too, the app shows that connection. Windows reports the firmware version only over the cable; over the receiver or Bluetooth it reports the radio's own version.

## USB interfaces

On Windows every top-level collection is a separate device path.

| Interface | Usage page / usage | Role |
|---|---|---|
| 0 | `0x0001` / `0x06` | Boot keyboard |
| 1 | `0x000C` / `0x01`, `0x0001` / `0x80`, `0x0001` / `0x06`, `0x0001` / `0x02`, `0xFFFF` / `0x01` | Consumer control, system control, NKRO keyboard, mouse, and a vendor collection (report `05`, 3-byte input) |
| 2 | `0xFF68` / `0x61` | Screen channel |
| 3 | `0xFF13` / `0x01` | Command channel |

### Report sizes

Read from the report descriptors (`kb descriptors`), and kept as test data in `crates/kb-core/src/shape.rs`:

| Collection | Descriptor | Input | Output | Feature | Report IDs |
|---|---|---|---|---|---|
| Command, `FF13` | 48 bytes | 64 bytes | 64 bytes | 64 bytes | none |
| Screen, `FF68` | 35 bytes | 64 bytes | 4096 bytes | none | none |
| Vendor, `FFFF` | 23 bytes | 3 bytes (report `05`) | none | none | yes |

Windows adds a report ID byte of `00` in front, so a command travels as 65 bytes and a screen page as 4,097. In a 20-second passive listen on the `FF13` and `FFFF` collections, the keyboard sent no input reports at all.

These shapes are what the app checks when it finds a keyboard on the cable, and again before it uses a channel (`kb_core::shape`). Keyboards of the "AA" family, some of which share the AK980 PRO's USB IDs and name, put 64-byte commands on `FF68` and add an `FF67` collection. They fail this check; when the model file lists an "AA" mode for them, they are driven in that family ([Telling the families apart](#telling-the-families-apart)). A keyboard whose channels fit neither family gets nothing and is listed as unsupported.

## The command channel

Every command is a 64-byte **feature report** on `FF13`. A session sends headers and the data packets a header announces, and ends with `04 02`, in some sessions followed by `04 F0`. The keyboard's answer to each header is read back with GET_FEATURE.

| Payload byte | Content |
|---|---|
| 0 | `04`. This is data, not a report ID. |
| 1 | Opcode |
| 2 | Argument: the screen slot for `04 72`, otherwise 0 |
| 3–7 | 0 |
| 8–9 | How many 64-byte data packets follow, little-endian |
| 10–63 | 0 |

Data packets are raw 64-byte payloads without a header. Lighting, clock, table and macro data carry the two bytes `AA 55`: at bytes 14–15 of a lighting packet, at the very end of the others.

### Answers

The echo repeats the header with a status in byte 3. A GET_FEATURE before anything has been sent returns 65 zero bytes.

| Echo | Status seen |
|---|---|
| `04 18`, `04 13`, `04 28`, `04 72` | `01` |
| `04 19` | accepted (not `FF`) |
| `04 20` | `00` |
| `04 F5` | `00`, then `01` once the color table is ready |
| `04 02` after lighting, per-key colors, a keymap or macros | `01`, and in bytes 4–5 the 16-bit byte sum of the data received, little-endian |
| `04 02` after the clock or a screen upload | `01`, with a sum of 0 |
| `04 F0` after a keymap | `01` |

Only `FF` means refused. Both `00` and `01` count as accepted. The byte sum wraps at 16 bits; `kb-core` compares it with what it sent and stops the write on a mismatch. The keyboard now and then stalls a GET_FEATURE (Windows error `0x1F`); a retry after 5, 10 or 15 ms succeeds.

### Opcodes and sessions

These are the opcodes on the allowlist that the app uses. Each one was measured in the session shown; the number in brackets is the packet count in bytes 8–9.

| Feature | Session | Measured time |
|---|---|---|
| Built-in effect | `04 18` → `04 13` (1) → 1 data packet → `04 02` → `04 F0` | 285 ms (`kb`), 341 ms (app) |
| Per-key colors | an effect session with mode `0x80`, then `04 18` → `04 23` (9) → 9 packets → `04 02` → `04 F0` | 856 ms for 8 keys (`kb`), 869 ms for 97 keys (app) |
| Key mapping | `04 18` → `04 11` base layer or `04 27` Fn layer (9) → 9 packets → `04 02` → `04 F0` | 608 ms (`kb`), 631 ms (app) |
| Macros | `04 19` → `04 15` (pages) → the pages → `04 02` | 600 ms for 9 pages |
| Clock | `04 18` → `04 28` (1) → 1 data packet → `04 02` | 251 ms (`kb`), 250 ms (app) |
| Screen upload | `04 18` → `04 72` slot 1 (pages) → the pages on `FF68` → `04 02` | about 143 ms a page |
| Live frame (RAM only) | `04 20` (8) → 8 packets → `04 02` | 29.5 frames a second |
| Color read-back | `04 F5` (9) → 9 reads → `04 02` | the app reads every 250 ms |

`04 17` (keyboard options such as sleep and the Windows key lock) is not on the allowlist: it writes to flash and has not been measured. It goes on the list together with its encoder once it is.

`kb-core` keeps a fixed pause before and after configuration packets (`CMD_DELAY` in `crates/kb-core/src/sonix.rs`). Measured: a `04 02` sent right after the last read-back packet is not processed, the session stays open and the next read-back fails.

## Lighting

### Built-in effects

The effect packet carries the mode, a color, a rainbow flag, brightness (0–5), speed (0–5) and a direction, and ends with `AA 55` in bytes 14–15. The modes are 0 (off) to 19, and `0x80` selects the per-key table. For example, the packet `0B FF 00 00 00 00 00 00 01 05 03 00 00 00 AA 55` stores mode 11 in rainbow colors at brightness 5 and speed 3; the commit echo was `04 02 00 01 12 02`, a byte sum of `0x0212` (530), equal to the bytes sent. The app uses the same settings as the factory lighting (`EffectSettings::factory`).

Each directional effect moves in only two ways. Code 2 behaves like code 1, and code 3 like code 0:

| Mode | Code 0 | Code 1 |
|---|---|---|
| 10 | down | up |
| 11 | right | left |
| 12 | counter-clockwise | clockwise |
| 16 | a short train of lights moves forward along the LED order | backward |
| 18 | up and to the right | down and to the left |

Measured with `kb direction-probe`, which stores each effect with each code, reads frames back and estimates the motion.

### Per-key colors

The per-key table is 9 packets (576 bytes): entry `idx` at byte `idx × 4` as `idx R G B`, `AA 55` in the last two bytes, so the highest usable index is 142. As with [live frames](#live-frames-ram-only), `kb-protocol` writes every entry from 1 to 142 with its own index, so keys not given are stored as black.

### Brightness and color

- At brightness level `n`, a color value `v` is driven as `v × m[n] >> 10`, with `m = [0, 191, 382, 573, 764, 1016]`. Level 3 is about 56 %, not 60 %. Effects and per-key tables use the same scale; all 40 values measured at levels 1 to 5 match it exactly.
- Colors are stored with 8 bits per channel, and the firmware applies no gamma. LEDs respond linearly while screens don't, so the app converts colors with the user's calibration (gamma 2.2 by default) before it sends them.
- Num Lock (LED 32, white) and Fn (LED 96, red while the battery charges, off when it is full) are drawn by the firmware itself. They ignore effects, per-key tables and live frames, and they are not scaled by brightness.

## Live frames (RAM only)

`04 20` announces 8 packets: 512 bytes holding 128 entries of `idx R G B` at `idx × 4`. There is no `04 18` and no `04 F0`. The highest LED index on a key is 123.

- Nothing is written to permanent memory. When frames stop coming, the keyboard returns to its saved lighting, so the app re-sends the current frame every 50 ms.
- Measured with `kb live`: 177 frames in 6 seconds (29.5 a second) with 2 ms between packets.
- The firmware applies entries by their index byte, and an all-zero slot changes nothing. A frame that listed only some LEDs left the others showing their previous color, so every slot now carries its own index and missing LEDs are sent as black.
- A frame must be completed once its header is sent. If the data doesn't follow, the keyboard takes the next packets as frame data, later commands are lost and the next read-back fails. A complete frame recovers the session.
- About 1 frame in 100 is refused with `FF`; the next one goes through.
- Live frames show even when the saved lighting is off. The brightness level is not applied to them, so the app scales them with the table above.

## Read-back

`04 F5` returns the colors the keys show at that moment, including animated effects and live frames.

- The header must announce 9 packets. With a count of 0, only the first read on a connection worked: the session never closed, later reads were ignored and the commands after them were swallowed. With 9, eight reads in a row 250 ms apart all succeeded.
- The echo reads `00` until the table is ready, then `01`. Nine GET_FEATURE reads follow, 576 bytes of `idx R G B`, then `04 02`.
- Green and blue come back as they are. Red comes back as `2 × r mod 256`, so its top bit is lost and every red byte stands for two values. `kb-core` picks the one that fits what the app expects the keys to show; with nothing to expect (rainbow effects) it guesses from the frame.
- Keymotion has no measured way to read back the stored effect, the keymap, the macros or the screen image. The app keeps its own record of each, updated only after a write the keyboard confirmed.

## Key mapping

A layer is 144 entries of 4 bytes at `idx × 4`, the index being the key's LED index, with `AA 55` in the last two bytes. Writing a layer replaces all of it.

| Entry | Meaning |
|---|---|
| `00 00 00 00` | The factory default for that key. A layer of zeros is the factory layout. |
| `02 MODS KEY 00` | A key (HID keyboard usage) with modifiers, the bits as in the boot keyboard report. Shift+A: `02 02 04 00`; Ctrl+Shift+A: `02 03 04 00`. |
| `03 LO HI 00` | A consumer usage, little-endian (Volume up: `03 E9 00 00`) |
| `01 01 BTN 00` | A mouse button; `08` arrives in Windows as button 4 (back) |
| `05 03 00 00` | The key does nothing |
| `06 SLOT MODE COUNT` | Plays macro `SLOT`: mode 0 once, mode 1 `COUNT` times. Modes 2 and 3 have not been tested. |

All of these were checked by pressing the keys and watching the events in Windows. The Fn layer works on a key that has no Fn function of its own. The Fn key itself (usage `0xAF`) is never reassigned: without it, the Fn layer and the keyboard's own Fn functions would be gone.

## Macros

`04 19` opens a macro session and clears the stored macros; it needs no `04 18`. `04 15` announces the pages, the pages follow, and `04 02` closes with a byte sum that matches the image.

The image is a directory of 100 four-byte slots followed by one record per macro. Each step is two 4-byte events: the action (key or mouse button, down or up) and the pause after it, at least 10 ms. A test image of three slots (a two-letter word; an empty slot; a right click, a 200 ms pause and a key) took 9 pages, and the keys played every step with its pause.

## Clock

`04 28` announces one data packet: `00 01 5A`, then year minus 2000, month, day, hour, minute, second, `00` and the weekday (0 = Sunday), in binary local time, with `AA 55` in the last two bytes. The keyboard echoes that packet byte for byte, which is the proof of delivery here, since the `04 02` sum is 0 in this session.

Every clock packet also switches the screen to its clock page, so the app sets the clock automatically at most once a day, 2 seconds after the keyboard connects, plus whenever the user asks.

## The screen

The panel is 240×135 pixels (1.14 inch). Images are RGB565, little-endian, rows from top to bottom; a test pattern with colored corners and an arrow confirmed the orientation and the color order.

- **Format.** A 256-byte header (the frame count and one delay byte per frame, in 2 ms units), then the frames, padded to whole 4096-byte pages. One frame takes 16 pages.
- **Upload.** `04 18`, then `04 72` with slot 1 and the page count. Each page goes to the `FF68` collection as a 4096-byte output report, and the keyboard answers each one with an input report starting `01 5A 02 00`. `04 02` closes the upload, with a sum of 0, so the per-page answers are the proof of delivery.
- **Where it goes.** The upload replaces the single animation on the screen's GIF page (opened with Fn+Home), including the factory animation. The home page with the date and time is not affected. The picture stays after unplugging the cable and after switching to 2.4 GHz and back.
- **While it runs.** The screen shows LOADING and a percentage, and the keyboard keeps typing.
- **Speed.** The first page takes about 283 ms, then about 143 ms each (133 to 283 ms), which fits writing flash. One still image (16 pages) takes about 2.7 seconds, 16 frames (254 pages) 37 seconds, and the 135-frame factory animation (2,136 pages) 308 seconds.

If a page fails, the app closes the session with `04 02`. The GIF page then stays incomplete until the next upload.

## Battery and charging

- **USB:** the keyboard reports no battery level over the cable. Its descriptors declare no battery usage, and it sends nothing on its own. The firmware lights Fn red while it charges and turns it off when the battery is full; the app reads that through `04 F5` and shows the charging state.
- **Bluetooth:** the standard GATT Battery Service is readable (94 % in the first test).

Over Bluetooth the keyboard offers only standard HID reports (system control, boot keyboard with its LED output, mouse, NKRO keyboard, consumer control, Windows Dial for the knob, and Eject with the Apple Fn key) and the battery service. Its vendor GATT service is the radio chip's firmware-update channel.

## What is blocked, and why

In the "04 xx" family these are refused in the code, whatever the caller asks for. The byte sequences are not given here on purpose. The "AA" family has its own rules: [Safety rules](#safety-rules).

| Blocked | Why |
|---|---|
| Firmware-update and bootloader sequences, and the controller's in-system-programming commands | They switch the keyboard's controller into update mode. Keymotion never updates firmware, and a wrong firmware write can leave a keyboard unusable. `guard` refuses them at the start of any packet on both channels, and the encoders make sure user data (a color, a key entry, a macro page) can never start like one. |
| Every opcode not on the allowlist | Other projects list more opcodes that the firmware accepts, some of them destructive. None of them has been measured here, so their effect on this keyboard's memory is unknown. |
| Writing to the Bluetooth firmware-update service | It reprograms the radio chip. `kb_transport::ble` has no write function. |
| Feature reads on the screen channel, and screen pages sent as SET_REPORT | On related keyboards, a feature read locked the firmware until power was removed, and pages sent as SET_REPORT crashed it. Pages always go as output reports, and `kb-transport` refuses GET_FEATURE on `FF68`. |
| `04 F0` after a screen upload | Other projects report that it restarts the animation and the upload doesn't stay. The upload is closed with `04 02` only. |
| Uploads over 140 frames or 2,215 pages | On an AULA F108 Pro, an animation past its limit overwrote the keyboard's menu graphics for good. The largest upload measured here is 135 frames. |
| Commands to the 2.4 GHz receiver | Nothing has been measured through it here. |

## The "AA" family: firmware 769

AJAZZ's firmware 769 for the AK980 PRO (version 3.01) replaces the commands above with the "AA" family, which AJAZZ's web tools and several related keyboards (AK820 Pro, AK980 MAX, MK87 and others) speak too. The packets and their guard are in `crates/kb-protocol/src/aa/`, the driver in `crates/kb-core/src/aa.rs` and `crates/kb-core/src/aa/`.

<Aside type="caution" title="Not yet measured on a 769 keyboard">
No keyboard on firmware 769 was available while this driver was written. What follows comes from what owners of 769 keyboards shared (the USB descriptors that **Request support** collects, and one device-information reply), from AJAZZ's own tools, read but never run against a keyboard here, and from measurements other projects made on related keyboards of this family. The driver was tested against a simulated keyboard that behaves this way. The first tests on a real 769 keyboard are planned for the [beta](/keymotion/developers/contributing/#beta-pre-release); until they pass, the "AA" mode lists no tested firmware, so the app asks before the first write of every session. [Still unverified on a real 769](#still-unverified-on-a-real-769) lists what is open.
</Aside>

### Identity and channels

On the cable a 769 keyboard reports VID `0C45`, PID `8039`, `bcdDevice` `0x0301`, manufacturer `SONiX` and product `AK980 PRO`. AJAZZ's tools also know an AK980 PRO of this family on PID `8009`, the IDs of firmware 1.06, so the IDs alone never decide the family.

| Interface | Usage page / usage | Role |
|---|---|---|
| 0 | `0x0001` / `0x06` | Boot keyboard |
| 1 | as on firmware 1.06 | Consumer control, system control, NKRO keyboard, mouse and the `FFFF` vendor collection |
| 2 | `0xFF68` / `0x61` | Command channel |
| 3 | `0xFF67` / `0x61` | Screen channel |

| Collection | Input | Output | Feature | Report IDs |
|---|---|---|---|---|
| Command, `FF68` | 64 bytes | 64 bytes | none | none |
| Screen, `FF67` | 64 bytes | 4104 bytes | 64 bytes, never used | none |

With Windows' report ID byte in front, a request travels as 65 bytes and a screen packet as 4,105. Each channel takes output reports no longer than its own report descriptor declares (`kb_transport::descriptor`), so a 4 KiB report can never reach the 64-byte command collection, and a channel whose descriptor can't be read writes nothing at all. Feature reports belong to the "04 xx" command channel only: `kb-transport` refuses SET_FEATURE and GET_FEATURE on every other usage page, `FF67`'s declared feature report included.

### Telling the families apart

The model file lists a cable mode for each family, each with its `protocol` ([How the family is chosen](/keymotion/developers/adding-a-keyboard/#how-the-family-is-chosen)). The report descriptors, which Windows keeps and which can be read without sending anything, decide which one a keyboard is:

| Family | Command channel | Screen channel |
|---|---|---|
| "04 xx" | `FF13`: 64-byte feature and output reports, no report IDs | `FF68`: 4096-byte output reports |
| "AA" | `FF68`: 64-byte output and input reports, no feature report, no report IDs | `FF67`: 4104-byte output and 64-byte input reports, no report IDs |

The two never overlap. Before an "AA" channel is opened (`kb_core::aa::open_channel`), its descriptor must fit again and declare exactly the 65 or 4,105 bytes the protocol uses, and the keyboard must report a product name: a SONiX controller in its bootloader can keep the keyboard's IDs and report an empty name, and nothing is sent to it.

### Requests and replies

Every request is a 64-byte **output report** on `FF68`. This family has no feature reports.

| Byte | Content |
|---|---|
| 0 | `AA` |
| 1 | Command |
| 2 | LEN: data bytes in this request, 1–56 |
| 3–4 | ADDR: where the data starts in the block, little-endian |
| 5 | 0 |
| 6 | LAST: 1 on a block's last chunk, otherwise 0 |
| 7 | 0 |
| 8–63 | LEN bytes of data, the rest 0; a read sends none |

The keyboard answers each request with a 64-byte input report: `55`, then the command, LEN and ADDR repeated, then 56 bytes that hold the data of a read or echo the data of a write. There are no sessions, no checksums and no pauses between commands.

- **Chunks.** A block longer than 56 bytes travels in 56-byte chunks, each answered before the next one goes: a 512-byte table takes ten requests, nine of 56 bytes and one of 8. LAST marks the last chunk, except in the macro table, which is written with LAST on no chunk.
- **Matching.** The driver takes a reply only when its command and address match the request, so a late answer to an earlier try never counts for the wrong chunk. The echo of a write must repeat the data sent, byte for byte.
- **Waiting.** Half a second for most answers, one or two seconds for the big table writes and for each screen packet, 50 ms for each chunk of a live frame. A request without an answer is sent again, up to three tries in all. A write that fails, or writes fewer bytes than it should, is not: hidapi can leave it pending, so the channel is closed and opened again, and the keyboard is read again before anything is written.
- **Other reports.** Reports that are not the awaited answer are skipped and counted. `55 FC 05` means the keyboard was reset (with a key combination, for example): everything the driver knew is stale, and nothing is written until it has read the keyboard again. Many unexpected reports mean that another program talks to the keyboard, such as AJAZZ's web tool in a browser, which can't be found by its process name.
- **Echo is not proof.** An echo says the keyboard took the data, not that it kept it, so every table is read back after it is written.

### What Keymotion reads and writes

Only these commands pass the guard (`kb_protocol::aa::guard`):

| Command | Size | Use |
|---|---|---|
| `10` read | 48 bytes | Device information. Always the first request. |
| `11` read | 56 bytes | The keyboard's system options, kept in the backup. Never written. |
| `12` read, `22` write | 512 bytes | Base keymap layer |
| `16` read, `26` write | 512 bytes | Fn keymap layer |
| `1C` read | 512 bytes | The factory Fn layer |
| `13` read, `23` write | 16 bytes | Lighting effect |
| `14` read, `24` write | 512 bytes | Per-key color table |
| `15` read, `25` write | 400 bytes and the macros | Macros |
| `33` read | 512 bytes | The colors the LEDs show right now |
| `32` write | one frame | Live frame, RAM only |
| `34` write | 24 bytes | Clock |
| `50` write, on `FF67` | 4104-byte packets | Screen upload |

Every other command is refused, on both channels: among them the option write, the factory reset, the firmware update and raw flash commands, LED animations, calibration and profile switching. `FF67` takes nothing but `50`, and `50` goes nowhere else.

The device information, as Keymotion reads it:

| Bytes | Field |
|---|---|
| 2–3 | Macro memory in bytes (3072 on 769) |
| 4–7 | VID and PID, little-endian |
| 8–9 | Firmware version as in `bcdDevice` (`01 03`, version 3.01, on 769) |
| 14–15 | Model code (`0x0033` on 769) |
| 16 | 0 on the cable, 2 through the receiver |
| 17 | Battery level in percent, on the cable too |
| 18 | Charge state |
| 22–23 | Most screen frames the firmware takes (0: not reported) |
| 28 | Screen orientation; 255 means no screen |
| 32 | Firmware status; 1 means waiting for a firmware update |

The first 19 bytes a real 769 keyboard sent on the cable were `40 00 00 0C 45 0C 39 80 01 03 FF FF 01 00 33 00 00 64 02`: battery 100 %, charge state 2. What charge state 2 means is not known.

### Effects and per-key colors

The effect is 16 bytes: `MODE R G B FF 00 00 00 RAINBOW BRIGHTNESS SPEED DIRECTION 00 00 AA 55`.

- The modes are those of the "04 xx" family (0 off to 19), 128 (`0x80`) for the per-key table, and 20 and 21, which show the per-key table too.
- Brightness and speed are 1–5 in this family, not 0–5. The app keeps its 0–5 scale and maps it through one table: 0 and 1 become 1, 2 to 5 stay as they are. Nothing outside 1–5 is ever written. The direction (0–3) goes as given.
- On related keyboards the color reads back as `FF FF FF` after a write, although the keys show the color written. So only the mode and the levels are compared after a write, and the driver remembers the color it wrote.
- The per-key table is 512 bytes: 128 entries `i R G B`, entry `i` for the key whose "AA" index is `i` (the model file's `aa`, not its LED number). A write gives every key of the layout its color, black when none is given, and keeps every other entry as it was read, entries 126 and 127 included: some keyboards of this family keep `AA 55` in the last two bytes. Every entry a write changes must start with its own index.
- `33` returns the colors the LEDs show at that moment, effects included; the app's mirror reads it. Red comes back whole, so the "04 xx" read-back decoding is not needed.
- The firmware's own Num Lock and Fn lights are "AA" indices 29 and 85, inferred from their keys.

### Live frames need a per-key mode

`32` shows one frame from RAM and stores nothing: `i R G B` for every key of the layout, in the model file's key order rather than the 128-entry table, in 56-byte chunks that are each echoed. Keys not given are sent black.

- Frames show only while the effect is in mode 20, 21 or 128, and in any other mode the driver refuses to send one. On related keyboards, the keyboard goes back to its stored lighting about 5 seconds after the frames stop.
- So the app **arms** the keyboard before the first frame of a live stream: unless the effect already is in one of those modes, it stores the effect in mode 128 with everything else kept, and remembers the effect it replaced. When the stream ends it **disarms**: it writes the remembered effect back. Both are writes to the keyboard's memory and pass the same checks as a save.
- A color that would, together with its neighbors in a chunk, form one of the bootloader sequences ([Safety rules](#safety-rules)) is changed by one step in one channel, which can't be seen. Index bytes are never changed.

### Keymap layers

A layer is 512 bytes, 128 slots of 4 bytes `PAGE P1 P2 P3`; slot `i` is the key whose "AA" index is `i`. These are the entries Keymotion writes:

| Entry | Meaning |
|---|---|
| `00 00 00 00` | The key's factory function |
| `02 MODS KEY 00` | A key with modifiers, the bits as in the boot keyboard report. A modifier on its own is its usage: `02 00 E0 00` to `02 00 E7 00`. |
| `03 LO HI 00` | A consumer usage, little-endian |
| `01 01 BTN 00` | A mouse button: 1 left, 2 right, 4 middle, 8 back, 16 forward |
| `01 03 01 00`, `01 03 FF 00` | Wheel up, wheel down |
| `06 SLOT MODE COUNT` | Plays macro `SLOT`: mode 0 once, mode 1 `COUNT` times, mode 2 until the key is pressed again |

- **Read, change, write.** A layer is always written whole. The driver reads it fresh, changes only the slots it was asked to, writes it, reads it back and compares. A layer that would not change is not written.
- **Never reassigned:** the Fn key (slot 85) and the knob (slots 13–15).
- **Firmware functions.** The Fn layer holds firmware functions (page `0D` with a 24-bit id), such as brightness steps and, on related keyboards, a factory reset on Fn+Space. A write never introduces one, nor a two-function entry (pages from `80` up), an entry that AJAZZ's own software runs (page 5) or a combination (page 7): these stay only in the slot where the fresh read found them. 23 function ids that reset the keyboard, start a test or calibration mode, switch between USB and wireless or NKRO modes, or lock the driver or macros out are refused by name. Every keymap write is checked as a whole table against the read it was built from.
- An entry the driver can't express as an action stays as raw bytes and goes back untouched.
- Not offered in this family yet: "the key does nothing" (the vendor's encoding suggests `02 00 00 00`, but no AJAZZ tool writes it), a double click, and a macro that repeats while the key is held, which this family doesn't have. The "04 xx" family's "does nothing" entry, `05 03 00 00`, would be a page 5 entry here and is never written.

### Macro table and blocks

- Addresses 0–399 hold 100 little-endian 4-byte addresses, one per macro slot (0: no macro). From address 400 follows one block per macro: a 4-byte header whose first two bytes hold twice the number of entries, then 4-byte entries `DELAY_LO DELAY_HI CODE FLAG`.
- The flag is `B0` or `30` for a key going down or up, `90` or `10` for a mouse button. The delay is the pause after the entry, 5 to 65,535 ms; shorter pauses are raised to 5 ms, except after the last entry.
- A write sends the table first, with LAST on no chunk, then the blocks from address 400 with LAST on their last chunk, and reads both back.
- The blocks take at most 512 bytes (4 per macro and 4 per entry), for at most 99 macros. AJAZZ's own tool keeps this keyboard to that, although the firmware reports 3072 bytes of macro memory; the limit goes up only once a real keyboard shows that more works.
- Macro names are not stored on the keyboard.

### Setting the clock

`34` carries `5A 01 5A`, then the year minus 2000, month, day, hour, minute, second and weekday (0 = Sunday) in binary local time, padded with zeros to 24 bytes. There is no session; the echo is the proof of delivery. Whether the screen switches to a clock page depends on the firmware; on 769 it reportedly doesn't.

### Screen uploads

- **Packets.** 4104 bytes each, on `FF67`: `AA 50`, the packet's number and the number of packets (both little-endian), `50 06`, then 4096 bytes of the image. The last packet is padded with zeros.
- **Image.** As in the "04 xx" family: a 256-byte header (the frame count, the delay of every frame but the last in 2 ms units, a 0, then `FF`), followed by the 240×135 frames in RGB565 little-endian, with no padding between them. One frame takes 16 packets, 140 frames take 2,215.
- **Answers.** Each packet waits for `FF67`'s answer `55 41 00 01` before the next one goes. But `FF67` answers every packet this way, whatever it holds: the answer is no proof that the screen changed. A command channel request sent to `FF67` would be answered the same way, with an unknown effect; none is ever sent there.
- **Limits.** At most the frame limit the keyboard reports in its device information, never more than 140; when it reports none, 140. A keyboard that reports no screen gets no upload. The guard checks every packet before the first one is sent.
- **The command channel stays silent.** On a related keyboard, live frames sent during an upload left its first packet unanswered, and a battery reading reset the USB connection. The driver holds the command channel for the whole upload: live frames, the mirror, the clock and device readings wait until it ends.
- **Cancelling** stops before the next packet. The screen stays incomplete until the next upload.
- **The clock page.** On 769, an upload reportedly takes the place of the factory screen with the date and time, and only a full factory reset brings that screen back (Fn+Space on the keyboard, which also erases keys, macros and lighting). One source reports this, and it is not confirmed. Before the first upload to an "AA" keyboard, the app says so and waits for the user's yes.
- Whether an upload is kept in flash or in RAM differs between related keyboards and is not known for 769. The app treats it as a flash write and counts it against the daily upload limit.

### Battery on the cable

The device information reports the battery level and a charge state on the cable too, which firmware 1.06 doesn't. The app shows the battery while the cable is plugged in.

### Safety rules

These hold in the code, whatever the caller asks for:

1. **No feature reports and no SET_REPORT** on an "AA" keyboard. Requests and screen packets are output reports only. On a related keyboard, the check that switches to the bootloader sits where control transfers are handled, which is where those would arrive.
2. **One way out.** Every packet on both channels goes through one function that runs the guard first: the exact length of its channel, report ID 0, the `AA` marker, a command on that channel's list, clean header bytes, no data in a read, effect values inside this family's ranges, the clock's marker, and a screen header whose packet number is below the count, with at most 2,215 packets and 1–140 frames.
3. **Bootloader sequences.** Two byte sequences that switch a SONiX controller into its bootloader, the one AJAZZ's 769 updater uses and SONiX's generic one, are refused at any position in any packet. The byte sequences are not given here on purpose.
4. **Signs of the bootloader.** A keyboard in its bootloader can keep its USB IDs and report an empty product name. A USB mode never matches a keyboard without a name, and no "AA" channel of one is opened.
5. **Firmware functions** are never written to a new slot, and the dangerous ones are refused by name ([Keymap layers](#keymap-layers)).
6. **Read, change, write.** Tables are built from a fresh read and change only where asked; entries 126 and 127, the Fn key and the knob stay as read.
7. **A full read before the first write.** The driver writes nothing until it has read everything the keyboard lets the host read: the device information, the options, both layers and the factory Fn layer, the effect, the per-key table and the macros. That read is the backup the app keeps before its first write to the keyboard. The driver can write a backup back: both layers, the effect, the per-key table and the macros, never the options, with the Fn key, the knob and the table tails kept as the keyboard has them now, and only to a keyboard with the same IDs and model code as the one the backup came from. The screen can't be read back, so no backup holds its image.
8. **Sanity gate.** Writes open only when that full read looks like the keyboard the driver knows: every block has its length; the device information's VID is `0C45`, its PID and firmware version are the ones USB reports, and its firmware status is 0; every keymap entry is on a known page; the effect has a known mode, levels of 1–5 (unless it is off) and a direction of 0–3; every per-key entry starts with its own index; every macro address lies inside the macro memory and its block reads. Otherwise the keyboard stays read-only, and the reasons are kept for the report the user is asked to send. A reset notice, or a full read that didn't finish, closes the gate again.
9. **Firmware status.** When the device information says the keyboard waits for a firmware update, nothing else is read or written. Keymotion never updates firmware.
10. **No command channel traffic during an upload** ([Screen uploads](#screen-uploads)).
11. **The app's write gate still applies:** one keyboard on the cable, no conflicting program, and a tested firmware version or the user's yes for this session.

Never sent to an "AA" keyboard: any "04 xx" command (on a related keyboard, the "04 xx" screen upload command erased the stored picture), anything through the 2.4 GHz receiver, and anything at all when its channels don't have this family's shape.

### The simulated keyboard

`kb_core::aa::sim`, behind the cargo feature `sim` (always on in kb-core's own tests, not part of the app's release build), is an AK980 PRO on firmware 769 in memory: both collections over one shared state, answering as this section describes. Its device information is the real 769 reply above, it echoes and keeps writes, its effect color reads back `FF FF FF`, its `FF67` answers everything, and it shows live frames only in modes 20, 21 and 128. Faults make it misbehave on purpose: lost and stray replies, a reset notice, silent device information, corrupted reads, failed writes, wrong echoes, writes it doesn't keep. It also checks the driver: a packet the guard refuses, a keymap write that introduces a firmware function, a macro table chunk with LAST, or command channel traffic during a screen upload fails the test.

### Still unverified on a real 769

Nobody has run this driver against a keyboard on firmware 769 yet. The first tests are planned for the beta, from reading to writing, one step at a time. Until then these stay open:

- whether every key's "AA" index is the right physical key (three tables of AJAZZ's agree on all 97 keys);
- the brightness and speed ranges, whether level 1 is dim or off, which direction codes each effect uses, and whether the `AA 55` tail of the effect matters;
- whether live frames show once per-key mode is on, at what rate, and how the keyboard goes back to its lighting;
- whether `33` reports the colors on 769;
- the "key does nothing" entry, and whether the knob's slots can be written;
- whether more than 512 bytes of macros work;
- the screen: the frame limit the keyboard reports, the time per packet, whether a picture stays after unplugging, which page shows it, and whether it really replaces the clock page;
- whether a clock packet changes the screen's page;
- what charge state 2 means;
- the 2.4 GHz receiver of a 769 keyboard: nothing is sent through it.
